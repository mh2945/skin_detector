# ROADMAP — 고도화 사다리와 트리거

**원칙: ML 로 가기 전에 더 싼 개입을 먼저 소진한다.** L1·L2 는 학습 데이터 0장으로
성능을 크게 올린다.

```
L0 룰 기반 ──┬─ ICC < 0.6 ───────────→ L1 광학 개입 (편광 + 플래시 차분)   ← 무학습, 최우선
             ├─ κ<0.4 인데 ICC 높음 ──→ L2 (안정적으로 틀리는 중)          ← 무학습
             ├─ 절대 비교 필요 ───────→ L2 부위별 CCM (컬러차트)           ← 무학습
             ├─ 병변 개수 정확도 요구 → L3 소규모 지도학습 (병변만)        ← 현재 요구사항 아님
             ├─ L1+L2 후에도 실패 ───→ L4 학습 기반 색 불변 표현
             └─ 임상 등급 요구 ──────→ L5 전용 하드웨어 / 멀티스펙트럴
```

---

## L0 — 룰 기반 (현재 구현)

**비용** 3~4주 · **산출** 판정 + 재사용 가능한 `core/` + 데이터 레이어

`core/` 6개 파일과 478 인덱스 테이블은 어느 경로로 가든 버려지지 않는다.

## L1 — 광학 개입 ★ 최우선 고도화 (무학습)

**트리거**: ICC < 0.6, 또는 정반사가 오검출을 지배. **또는 그냥 Phase 1에서 같이 테스트.**

1. **교차 편광** — 렌즈와 광원에 편광 필름을 직교로 붙이면 **정반사가 물리적으로 완전히
   제거된다.** 피부과 영상 장비가 하는 일이 정확히 이것이다. 부품값 수천 원으로
   COLOR_SCIENCE §6 전체를 불필요하게 만든다.

2. **플래시 on/off 쌍 차분** — 두 장을 차분하면 **주변광이 상쇄되고 플래시 성분만 남는다.**
   즉 **SPD 가 알려진 광원**을 얻는다. 소프트웨어만으로 **혼합 조명 문제(LIMITS §3-7)를
   직접 해결**한다.
   → `validate.py flashpair` 가 이미 준비돼 있다. **Phase 1 에서 반드시 같이 테스트한다.**

**기대 이득**: ICC +0.10~0.20, 병변 precision +0.1~0.2. **학습 데이터 0장.**

## L2 — 부위별 CCM 캘리브레이션 (무학습)

**트리거 두 가지.**
① 피험자 간·기기 간 **절대 비교**가 요구사항이 될 때.
② **ICC 는 높은데 인간 순위 상관 / κ 가 낮을 때** — 안정적으로 틀리고 있다는 신호다
   (LIMITS §3-13 이 예측한 실패 모드).

컬러차트를 동반 촬영해 기기·부위별 보정행렬을 산출한다.
근거: Kang & Kim — 전역 CCM 시 MI ICC 0.80, **부위별 CCM 0.95**.
비용 차트 5~10만원 · **기대 ICC 0.90+**. 부작용: UX 훼손 → 내부/전문가용 한정.

> PoC 에서는 차트를 쓰지 않기로 확정했다. 그 대가가 LIMITS §3-13 이다.
> 이 한계가 실제로 문제가 되는 순간 차트를 사서 세션을 다시 찍는다.

## L3 — 소규모 지도학습 (병변만)

**트리거**: **병변 *개수* 정확도가 요구사항으로 승격될 때.**
현재 성공 기준은 부위 단위이므로 **L3 는 필수 경로가 아니다** — 이것이 목표 1을
부위 단위로 정의한 가장 큰 실질적 이득이다.

> **상태 (2026-08-28): Phase 1 착수.** 라벨링 도구가 들어왔고 평가셋이 다음이다.
> 트리거를 당긴 것은 실사진에서 드러난 §3-9(농포의 흰-노란 중심이 붉은 블롭
> 모델을 파괴함)이며, **precision/recall 이 _미측정_ 이라 룰을 고쳐도 좋아졌는지
> 알 수 없다는 사실**이 결정적이었다. 전체 계획은 `docs/L3_PLAN.md`.

다만 가장 약한 고리는 여전히 병변이고, `feedback.json` 의 "놓침/과검출"이
병변에 집중되기 시작하면 그때가 신호다. **피드백 데이터가 이 판단의 근거가 된다.**

- **데이터**: 얼굴 300~500장 클릭 라벨(세그멘테이션 아님 — 점만 찍으면 되므로 빠르다).
  필요시 ACNE04 보강. **라이선스·도메인 갭 검토 선행.**
  이 시점에 `scripts/label.py` 를 추가한다. **2026-08-28 추가됨** — Phase 1 착수.
  계획은 `docs/L3_PLAN.md`, 인수인계는 `docs/L3_GUIDE.md`.
- **모델**: 얼굴 크롭 대상 소형 anchor-free 검출기(FCOS/CenterNet + MobileNetV3).
  **입력이 이미 정규 IPD 프레임이라 스케일이 고정** → 학습이 쉽고 모델이 작아진다.
- **L0 가 버려지지 않는다**: 색 정규화·마스킹·품질 게이트를 그대로 전처리로 쓰고
  ΔEI 맵을 **추가 입력 채널**로 넣는다. RGB 만 넣는 것보다 데이터 효율이 좋다.
- 비용 라벨링 2~3일 + 학습 1주 · **기대 precision 0.7–0.85** · 온디바이스 10~20ms

## L4 — 학습 기반 색 불변 표현

**트리거**: L1 + L2 를 다 하고도 ICC < 0.6 (즉 FAIL).
학습된 color constancy 또는 조명 증강 임베딩. 동일 얼굴 다중 조명 쌍이 대량 필요해
**수집 비용이 L3 보다 훨씬 크다.** 이 단계는 "룰 기반 우선" 방침을 공식 철회하는 시점이다.

## L5 — 전용 하드웨어 / 멀티스펙트럴

**트리거**: 임상 등급 절대 측정 요구.
편광 + 고정 조명 + 좁은대역 필터(542/577 vs 660nm) → **진짜 헤모글로빈 정량.**
이 시점엔 소프트웨어가 아니라 제품 정의가 바뀐 것이다.

## 모바일 포팅 (L0 통과 시)

**그대로 넘어가는 것**: `core/` 6개 파일 전부 + 478 인덱스 테이블 + 색 상수 + 흡광계수 CSV.
세 플랫폼이 같은 `.task` 번들·같은 인덱스를 쓴다.

> **C++ 공유 코어를 권한다.** Android(NDK/JNI) + iOS(ObjC++ 브리지)에 **하나의 구현**.
> Kotlin/Swift 로 각각 다시 쓰면 2배 작업 + 두 구현이 갈라진다.
> 그래서 CONTRACT 6번(C++ 로 옮겨쓸 수 있는 스타일)이 있다.

**다시 써야 하는 것**: `imageio.py`, `render.py`, `face.py` 의 mediapipe 어댑터, `tune.py`, `web/`.
단 **`web/server.py` 의 `GUIDANCE` 표와 결과 화면 구성은 그대로 옮겨간다** —
문구는 코드가 아니라 자산이고, 웹에서 실제 사용자에게 검증된 문장이 모바일에서도 맞다.

**AWB/AE 고정** — 브라우저에서 못 하던 것을 여기서 되찾는다.
- **Android**: "락"보다 "명시적 고정"이 낫다. 락은 *수렴한 값이 무엇이든* 얼려 촬영마다 달라진다.
  `CONTROL_AWB_MODE_OFF` + 명시적 `COLOR_CORRECTION_GAINS`,
  `CONTROL_AE_MODE_OFF` + 명시적 `SENSOR_EXPOSURE_TIME`/`SENSOR_SENSITIVITY`.
  **토치 > 플래시**(사전 발광 측광 변동 없음).
  > 주의: 대부분 안드로이드 전면 "플래시"는 **화면 발광**이라 기기별·밝기별 SPD 가 다르다.
- **iOS**: 유리하다. `setWhiteBalanceModeLocked(with:)` 로 **게인을 명시 지정**할 수 있다.
  `setExposureModeCustom(duration:iso:)`, `setTorchModeOn(level:)`. Pro 는 `.dng` RAW.
- **공통**: HDR·벤더 뷰티 보정을 반드시 끈다. 실제 적용된 게인/ISO/노출을
  `CaptureMeta.awb_gains` 에 기록한다 — 필드는 이미 만들어 뒀고 지금은 `null` 이다.

**성능**: 768×768 에서 블러 몇 개 + 4스케일 DoG → 최신 폰에서 수 ms.
병목은 랜드마커이고 그건 이미 최적화돼 있다.

> **어느 경로로 가든 Alchera FaceSDK 는 도움이 되지 않는다**(피부 모델 부재).
> 모델 활용은 L3 이후 자체 학습 또는 공개 데이터셋 경로다.
